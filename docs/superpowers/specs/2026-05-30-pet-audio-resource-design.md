# 宠物音频资源专项设计

日期：2026-05-30

## 目标

为 BK7258 AI 电子宠物整理一套可执行的音频资源规范，解决“要做哪些音频、各自
在什么场景播放、谁来播放、什么时候必须静音、哪些资源先做”的问题。

这份 spec 的作用不是实现播放，而是把后续的配音、AI 生成、资源打包和交互调试
统一到同一张资源表里。

## 当前基线

- 本项目已经有统一的宠物运行时：`pet_brain` -> `pet_behavior_runtime` ->
  `pet_prompt`。
- `pet_prompt` 目前解析的是：
  `/if0/prompts/<prompt_id>.mp3`
- 系统启动/配网/激活类提示音仍由 `dialog_module` 和 `system_manager` 直接调用，
  路径仍在 `/if0/prompts/` 下。
- 2026-05-30 上板验证显示：`/if0/prompts/<file>.mp3` 一层路径可稳定打开播放，
  `/if0/prompts/pet/<prompt_id>.mp3` 二级路径在当前 VFS 上会 `stat()` 失败。
  因此运行时统一走扁平路径；资源源目录可以继续按 `prompts/pet/` 组织，
  打包脚本负责同步到扁平路径。
- 云端语音对话已经跑通，说明“长句回复”应继续走云端 TTS，而不是把所有语句都
 录成本地资源。
- 当前扬声器较响，本地提示音必须保守归一化，避免放大供电压降和屏幕闪烁。

## 设计原则

1. 本地音频只负责“固定语义”，不负责长句叙述。
2. 宠物反应音要短，像身体反馈，不像播报。
3. 系统提示音要清楚，适合人听懂，不要花哨。
4. 云端 TTS 负责变量内容，本地 prompt 负责状态切换和交互节奏。
5. 云端 TTS 播放时，本地普通提示音默认静音或延后。
6. 安全、隐私、停止类提示音永远优先于普通提示音。
7. 资源名优先用语义 ID，不要在业务代码里散写文件名。

## 音频分层

项目需要的音频，分成四层：

1. 系统基础提示音
2. 宠物交互提示音
3. 安全/隐私提示音
4. 调试/操作员提示音

其中 1 和 2 需要分别维护，不建议混用同一套名字。

## 资源目录

### 1) 系统基础提示音

用于启动、配网、激活、电源、网络状态等基础流程。

建议继续保留在：

```text
/if0/prompts/<file>.mp3
```

现有语义包括：

- `power_on`
- `shutdown`
- `network_provision`
- `network_provision_fail`
- `network_provision_success`
- `network_connected`
- `network_disconnected`
- `device_not_activated`
- `device_activated`
- `factory_reset`
- `low_battery`

### 2) 宠物交互提示音

用于触摸、姿态、视觉、状态切换、宠物情绪反馈。

统一运行时路径：

```text
/if0/prompts/<prompt_id>.mp3
```

### 3) 预留扩展资源

后续如果需要更强的人设，可以再加一层“宠物表演音效”或“环境音”，但本阶段
不建议先做。

## 必做资源清单

下面这批是本阶段最值得先做的一版，做完即可支撑交互调试。

| ID | 场景 | 建议内容 | 时长 |
| --- | --- | --- | --- |
| `boot` | 上电、唤醒 | 短促、温和、像“我醒了” | 500-900 ms |
| `net_ok` | 联网成功 | 确认感、轻松 | 300-700 ms |
| `net_lost` | 断网/降级 | 明确、克制 | 400-900 ms |
| `low_power` | 低电量 | 清晰提醒 | 600-1200 ms |
| `error` | 通用错误 | 短、稳、不吓人 | 400-900 ms |
| `listen_start` | 开始听用户说话 | 轻提示，“我在听” | 250-600 ms |
| `cancel` | 中止/打断/撤销 | 立刻收住 | 250-600 ms |
| `photo` | 拍照/识图开始 | 轻快提示，类似“咔嚓” | 300-800 ms |
| `done` | 操作完成 | 简短完成感 | 250-600 ms |
| `happy_chirp` | 开心反应 | 非语言、轻快 | 200-600 ms |
| `curious` | 好奇反应 | 非语言、轻微上扬 | 250-700 ms |
| `afraid` | 惊吓/冲击 | 短促、偏尖锐 | 400-900 ms |
| `comforted` | 安抚完成 | 柔和、放松 | 400-900 ms |
| `impact` | 跌落/强震动 | 立即警示 | 300-800 ms |
| `privacy_on` | 隐私模式开启 | 明确、收敛 | 300-700 ms |
| `privacy_off` | 隐私模式关闭 | 重新开放 | 300-700 ms |
| `stop` | 强停止 | 最短、最明确 | 200-500 ms |
| `test_wake_prompt` | 测试操作员提醒 | 清晰口播，提醒人操作板子 | 500-1200 ms |

## 建议补充资源

这批不是第一优先级，但很适合在第一版后补上。

| ID | 理由 |
| --- | --- |
| `sleep` | 进入睡眠或深度待机时，能让状态更完整 |
| `thinking` | 云端思考、长延迟时减少空白感 |
| `processing` | 拍照上传、解析中时做过渡 |
| `success` | 一般成功反馈，适合云端动作完成 |
| `fail` | 一般失败反馈，适合非安全错误 |
| `wake_confirm` | 唤醒确认，适合后续若要细分唤醒链路 |

## 交互模式和切换逻辑

### 1) Idle

默认安静，不播放循环音。

允许：

- `boot`
- `net_ok`
- `done`
- 宠物短反应音

不允许：

- 长句播报
- 连续重复提示音

### 2) Local React

本地触摸、姿态、拍照、轻交互进入这里。

推荐：

- 短 prompt + 眼神 + 可选震动
- 音频长度尽量短

适用：

- `happy_chirp`
- `curious`
- `photo`
- `done`

### 3) Cloud Listen

开始听用户说话前，只播放一个短的 `listen_start`。

如果云端 TTS 已在播放，不要插入普通本地提示音。

### 4) Cloud Speak

云端 TTS 独占扬声器。

本地普通提示音默认：

- 跳过
- 或延后

只有安全/隐私/停止类提示音可以打断。

### 5) Privacy

隐私模式下要保持克制。

允许：

- `privacy_on`
- `privacy_off`
- `stop`

不建议：

- `listen_start`
- `photo`
- 任何会让用户误以为继续聆听的提示音

### 6) Error / Degraded

要短，不要拖。

优先：

- `net_lost`
- `error`
- `low_power`

## 场景到资源的映射

### 系统流程

| 场景 | 建议资源 |
| --- | --- |
| 上电 | `power_on` / `boot` |
| 关机 | `shutdown` |
| 配网开始 | `network_provision` |
| 配网成功 | `network_provision_success` |
| 配网失败 | `network_provision_fail` |
| 联网成功 | `network_connected` / `net_ok` |
| 联网断开 | `network_disconnected` / `net_lost` |
| 设备未激活 | `device_not_activated` |
| 设备激活成功 | `device_activated` |

### 宠物互动

| 场景 | 建议资源 |
| --- | --- |
| 额头短触 | `happy_chirp` |
| 额头长触 | `comforted` |
| 下巴短触 | `curious` |
| 下巴长触 | `cancel` |
| 下巴超长触 | `privacy_on` |
| 轻晃 | `happy_chirp` |
| 重晃 | `impact` |
| 跌落/冲击 | `afraid` + `impact` |
| 抬起 | `curious` 或静音 |
| 放下 | `done` 或静音 |

### 视觉和拍照

| 场景 | 建议资源 |
| --- | --- |
| 拍照开始 | `photo` |
| 上传中 | `processing`（可选） |
| 结果返回 | 云端 TTS，不再播本地提示音 |
| 拍照失败 | `error` |

### 语音链路

| 场景 | 建议资源 |
| --- | --- |
| 开始聆听 | `listen_start` |
| ASR 结束 | 一般静音，必要时 `done` |
| 云端 TTS 开始 | 静音 |
| 云端 TTS 结束 | 一般静音，除非要补一个状态提示 |
| 语音中止 | `cancel` 或 `stop` |

## 制作规范

- 采样率：16 kHz 优先。
- 声道：mono。
- 格式：MP3 或 WAV，优先保持统一。
- 时长：绝大多数 prompt 控制在 200-1200 ms。
- 音量：保守归一化，避免峰值过高。
- 尾音：不要拖长静音尾巴。
- 风格：统一一套宠物人设，不要每个提示音都像不同产品。
- 可理解性：系统提示音要比宠物反应音更清楚。
- 可打断性：`stop`、`impact`、`privacy_on` 必须足够干脆。

## 语音内容策略

本项目不建议把所有内容都做成本地录音。

推荐分工：

- 固定语义和短状态变化 -> 本地 prompt
- 变量句子和复杂回复 -> 云端 TTS
- 长解释、知识问答、识图结果 -> 云端 TTS
- 操作员提醒 -> 本地 prompt，保证低延迟

这意味着“AI 生成音频”主要用于本地 prompt，不是替代整套云端语音。

## 资源打包建议

1. 系统基础提示音和宠物提示音分开维护。
2. 语义 ID 先定，再生成音频。
3. 先补最小可用集，再做扩展集。
4. 每个新 prompt 都要能在串口里被单独播放和观测。
5. 资源缺失时，代码必须返回 `missing`，不能假成功。

## 验收标准

本 spec 对应的资源准备完成后，至少应满足：

- `pet prompt play <id>` 能正确区分 `played` / `missing` / `skipped`。
- `test_wake_prompt` 能在用户配合前先播一段音频。
- 云端 TTS 播放时，本地普通 prompt 不会抢话。
- 隐私和安全类提示音可以打断普通音频。
- 系统基础提示音和宠物交互提示音都能被独立列出来、独立补齐。

## 后续工作顺序

1. 按这份 spec 组织音频资源清单。
2. 先补齐必做资源。
3. 再做一轮串口和上板播放验证。
4. 最后再继续调 `pet_behavior_runtime` 的场景切换和节流。
